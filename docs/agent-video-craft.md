# 動画制作の暗黙知（どのエージェントでも同じ品質で作るために）

Claude・Codex・ChatGPT・人のだれが作っても同じ品質になるよう、作り手が普段は言葉にしないままやっている判断と手順を書き出したもの。
道具の使い方は各ラインの文書（`docs/style-shorts.md` / `docs/three-shorts.md` / `docs/longform.md`）、手順は playbook（`docs/style-shorts-playbook.md` / `docs/three-shorts-playbook.md`）にある。ここには **なぜそうするか** と **どこを見るか** を書く。

> 品質の最終判断は Yuto の評価が正しい。技術QAの合格や自己採点は「出せる」ことの確認であって、面白い・良いことの証明ではない（`docs/shorts-editorial-postmortem-20261017.md`）。

---

## 1. 作業のループ — 小さく作って、見て、直す

1. **尺と構造だけ**を先に出す（`--timeline-only`）。秒数と lint を見る。
2. **静止画**をシーンごとに出す（`--stills auto --scale 0.4〜0.5`、2D なら数秒、3D でも1分程度）。全部を横に並べて1枚にして見る。
3. **機械の目**を通す（Style Shorts は `--inspect`）。はみ出し・重なり・小さい文字・コントラスト・スマホUIの位置を数値で出す。
4. 直す。**1回の修正で直す原因は1つ**。直したら同じ時刻の静止画を出し、前と見比べる。
5. 全画風・全シーンに効くコード（エンジン・テーマ・字幕）を変えたら、**直した箇所以外が壊れていないか**をギャラリー（`tools/styles/gallery.mjs`）か全画風の `--inspect` で確かめる。
6. ここまで問題が無くなってから本番レンダリング（声・音楽・mux）。本番は時間がかかるので、静止画で分かる問題を本番に持ち込まない。
7. 本番の後は、contact sheet（1秒ごと）と 1フレーム目のスマホサイズ画像を見る。音は聞ける人が聞く。

> 画像を見られない環境のエージェントでも 3 は必ず回す。見られる環境でも 3 は省略しない（目視は疲れると見落とす。機械は見落とさないが意味は分からない。両方やる）。

## 2. 1コマを見るときの順番

上から順に見る。上で引っかかったら下は見ずに直す。

1. **スマホの大きさ（幅360px）で1秒見て、何の話か言えるか。** `review/first-frame-phone.png` は特にこれ。
2. **主役は1つか。** 視線が最初に行く物（大きな数字・顔・動いている物）が、ナレーションが話している物と一致しているか。
3. **文字**
   - 大きさ: 1080×1920 で字の高さ 30px 以上（フォントサイズ 34px 以上、横幅の 3.2% 以上）。軸の目盛りや出典も含む。
   - コントラスト: 背景と 4.5:1 以上。足りないときは縁取り・帯・影のどれかを付ける。灰色（`#888`）を明るい背景に置くと 3:1 前後で読めない。
   - はみ出し・折り返し: 2行目が1〜2文字だけになる折り返しは読みにくい（行を均等に割る。`wrapText` が自動でやる）。
   - 字幕と画面内の文字が重なっていないか。
4. **スマホのUIで隠れる場所**（9:16、縦横の割合）— ここに文字や大事な物を置かない。
   - 下 18%（y > 0.82）: タイトル・チャンネル名・説明
   - 右 14% の下半分（x > 0.86 かつ y > 0.5）: いいね・コメント・共有ボタン
   - 上 4%: 検索・タブ
   - 字幕は y ≤ 0.76（2行になっても 0.80 で止まる）。画面内の情報は y 0.08〜（字幕の y − 0.08）に収める。
5. **人物**: 顔が切れていない／字幕が顔にかかっていない／画面の端（左右 10%）に寄りすぎていない／暗い背景で黒い線の人物が消えていない。
6. **動き**: 静止画1枚では分からない。2つの時刻の静止画を並べ、歩く方向と体の向き、ポーズの変化、カメラの寄りを確かめる。
7. **前のシーンと画が変わったか。** 6秒以上同じ画が続くと離脱する（lint が警告する）。

## 3. 台本 — いつも無意識にやっていること

- **三つを同時にそろえる**: タイトル × 0秒の画 × 最初の一言は同じ約束を別の層で言う（詳しくは `docs/short-drama-design.md` §1）。最初の一言は問いか、意外な数字。
- **大きな数字は生活の単位に翻訳する。** 38万4400km → 「時速4kmで休まず歩くと約11年」→「小学1年生が高校生になる」。数字を聞いた人が自分の時間・体・お金で想像できる形まで落とす。
- **比較で縮尺を作り、最後に縮尺を壊す。** 徒歩 → 車 → 飛行機と段階的に短くし、最後に光（1.3秒）で桁を飛ばす。段階が無いと最後の驚きが立たない。
- **1 beat = 新しい情報1つ + 新しい画1つ。** 情報が増えない beat は削る。
- **ナレーションと画面の文字を同じ言葉にしない。** 画面は数字・キーワード（「約11年」）、声は文脈（「なんと約11年。小学1年生が高校生になる」）。同じ文言を読み上げるだけの画は「スライドを読む動画」になる（2026-10-17 の不合格例）。
- **字幕の区切り（`／`）は意味の切れ目**に入れる。1チャンク 14〜20字が読みやすく、26字が上限。1チャンクは 2〜3 秒。
- **締めは最初の問いに戻る**か、視点が一段ひっくり返る一言。説明の言い直しや、オチのために足した小道具・決め台詞で締めない（本人が「狙いすぎ」と言う型。`docs/short-drama-design.md`「狙いすぎない」）。
- 話し言葉で、1文に情報1つ。漢字の連続や数字の羅列は耳で追えない。

## 4. 数字と事実

- 数字・固有名詞は一次情報で確かめ、`sources` に書く（説明文に「出典」として出る）。確かめられない数字は使わない。
- **計算した数字はコードで計算して、式を残す。** 例（月まで歩く）:
  `384400 / 4 = 96100 時間 → / 24 = 4004 日 → / 365 = 10.97 年`、`384400 / 100 / 24 = 160 日`、`384400 / 900 / 24 = 17.8 → 約18日`、`384400 / 299792 = 1.28 → 約1.3秒`。
  丸め方（約・切り上げ）を動画全体でそろえる。
- 模式図（ルート・分解図）は「模式図」と画面に書く。実在の地名・所要時間を出すときは地図サービス等で確かめる。
- 実在のキャラクター・ゲーム・ブランドの名前・ロゴ・特徴的な見た目を出さない。参考にするのは「どんな種類の見た目があるか」まで。

## 5. テンポの数値（実測）

| 項目 | 値 |
|---|---|
| VOICEVOX 青山龍星 speed 1.15 | 約 8 モーラ/秒 |
| **推定タイミング（VOICEVOX なし）と実音声の差** | **実音声は推定の約 1.3 倍**（16.9s → 22.0s、17.0s → 21.9s） |
| 最初の声 | 0.3 秒以内（Style Shorts の既定 `pre` 0.06） |
| beat の長さ | 2〜6 秒 |
| 全体 | Style Shorts 20〜45 秒（上限 58）、3D コント 35〜50 秒 |

推定で尺を決めるときは 1.3 倍して考える。実音声で長すぎたら、台詞の文字を変える前に `pre` / `post` を詰める（3D playbook §5.1 と同じ順番）。

## 6. 画の作り方

- **縦画面の見える幅は狭い**: 3D で距離 d、縦の画角 fov のとき、見える横幅は `2·d·tan(fov/2)·0.5625`。距離 3.4m・fov 40° で約 1.4m。人物は中央寄り（stage の x は ±0.8 以内、歩かせるなら -0.7→0.5 程度）。
- **止まった画を作らない**: カメラはゆっくり寄るか流れる（`camera.zoom` → `to.zoom`）、人物は待機中も呼吸する（エンジンが自動）。全く動かない時間が 1 秒続くと止まって見える。
- **明暗**: 暗い背景に黒い線の人物は消える。エンジンは暗いセットで線画の人物を白に反転するが、新しいセットを足したら `DARK_SETS` に登録する。
- **字幕の位置と内容領域を分ける**: 内容は字幕の上に置く（`zone()`）。グラフの右端は x 0.8 まで（右の目盛りがボタンに隠れる）。
- **画風が題材に合わないときは画風を変える。** 合わない画風に無理に乗せると、画風の良さが出ない（例: ミニマル線画に棒グラフ）。各画風の「得意なシーン」（`catalog/styles.json` の `best`）を使う。
- **低解像度の画風（ドット絵・レトロ3D）では小さい文字や細い線を画の中に置かない。** 字幕・パネルで出す。
- 新しい見た目の部品は作品の中ではなくエンジン（`src/styles`）に汎用に作り、ドキュメントに書く。

## 7. 音

- 声 → 効果音 → BGM の順に重要。BGM は声の下で自動で下がる（ダッキング）。BGM の音量は 0.14〜0.18。
- 最終の音量は -14 LUFS（YouTube の基準）。`qa.mjs` が測る。
- **効果音は画が動くところにだけ付ける。** カットの位置に機械的に付けた効果音は不自然（2026-10-17 の不合格例）。Style Shorts の自動のシーン切替音は、画が動く遷移（pop / slide / flash / wipe）のときだけ鳴る。それ以外は beat の `do: [{ "at": "line", "sfx": "..." }]` で、見えている動作に合わせて置く。
- 驚かせる音・大きな音は 1 本に 1 回まで。
- 音は、人の耳で聞いていない限り「聞いた」と報告しない。測定値は聞いた代わりにならない。

## 8. 実際に起きた失敗と対策（Style Shorts を作ったとき、2026-11-17）

| 起きたこと | 原因 | 対策（今のコード） |
|---|---|---|
| フックの文字が最後まで出続けた | 「hook の次の役割付き beat まで」表示していた | hook の beat が終わったら消す（`render-style.mjs`） |
| 宇宙のセットで棒人間が見えない | 黒い線 × 黒い背景 | 暗いセットでは線画の人物を白に反転（`DARK_SETS`） |
| 字幕が「〜にな／る」と1文字だけ折り返した | 幅いっぱいで折り返していた | 行の長さを均等にする折り返し（`wrapText`） |
| 棒グラフが字幕に重なった | 内容の領域を固定値で置いていた | 字幕の y から内容の下端を決める（`zone()`） |
| ドット絵が粗すぎて読めない | ドットの大きさを出力解像度に対して決めていた | 1080 幅に対して 1/4（270×480 相当）に固定 |
| 3D のルートが建物に隠れた | カメラが低い・建物が高い | 真上寄りのカメラ、ルート付近の建物を低く |
| 3D で歩く人物が画面から出た | 舞台の x を広く取りすぎた | x の倍率を 0.62 に |
| **8 画風で字幕がスマホのUIの位置（y 0.80〜0.86）にあった** | UI の安全域を数値で決めていなかった | 字幕を y ≤ 0.76 に。`--inspect` が安全域を検査 |
| 灰色の補足文字が読めない（約 2.7:1） | `#888` を明るい背景に置いた | `muted()`（明るい背景 `#555`、暗い背景 `#bdbdbd`） |
| 暗い背景の上で黒い字幕が消えた（動くグラフ × 宇宙） | 字幕に縁が無かった | `plain` の字幕にも反対色の細い縁 |
| 効果音を足したら 3D の全作品の回帰レンダリングが走って落ちた | `catalog/sfx3d.json` の変更が 3D ラインの全作品再レンダリングを起こし、古い作品が今の lint で止まった | Style Shorts の音は `catalog/sfx-styles.json` に置く。共有カタログを触るときは他ラインの CI の発火条件を先に読む |

最初の全画風 `--inspect` では 37 件のエラーと 700 件以上の警告が出て、上の修正後は 0 件になった。目視だけでは安全域の問題に気づけていなかった。**機械の検査は目視の代わりではないが、目視の見落としを確実に拾う。**

## 9. 環境とリポジトリの注意

- VOICEVOX がローカルに無いときは、GitHub Actions（Style Shorts / 3D Shorts）で声付きの書き出しをする。`voices_only` で声だけ作って artifact を `outputs/three-voice/` に置けば、手元で本番レンダリングできる（声のキャッシュは Style Shorts と 3D で共通）。
- `outputs/` は git に入らない。人に見せるときは artifact か GitHub Pages のレビュー（`docs/review.md`）。
- 共有のカタログ（`catalog/sfx3d.json`、`catalog/asset-library.json`）を変えると他ラインの CI が全作品を再レンダリングすることがある。ワークフローの `paths` を先に読む。
- PR は gh CLI で作る。GraphQL が使えない環境（Claude Code のクラウド環境など）では REST を使う: `gh api repos/nomuonji/animation-factory/pulls -f title=... -f head=... -f base=main -F body=@body.md`。
- 速さの目安: 2D は 1080×1920 で 1 フレーム約 30ms（30 秒の動画が 30 秒前後）、3D は SwiftShader で 1 フレーム 0.5〜0.9 秒（30 秒で 8〜13 分）。比較やギャラリーは `--scale 0.4` で。

## 10. 報告の書き方

1. 何ができたか（動画・リンク）を先に。
2. 技術の結果（尺・音量・`--inspect` の件数・QA）と、内容の評価（未評価・本人の判断待ち）を分けて書く。
3. 自分で見て気になった点と、直さなかった理由。
4. 確かめていないこと（音を聞いていない、数字の出典が二次情報、など）を隠さない。
